# OSC 3110 config replacement

Inside a session, use `statusbar config` to replace the running layout:

```sh
statusbar config < FILE
cat FILE | statusbar config
```

The command reads the file and sends its contents through `/dev/tty`. It does
not send the file path. A successful command confirms that it sent the request;
the running session checks the new config separately. For normal use, see
[replacing the running config](config.md#replace-the-running-config).

This page describes the terminal message for programs that send it directly.

## Message format

statusbar uses one message in the OSC 3110 (ELLO) namespace:

```text
ESC ] 3110 ; STATUSBAR ; CONFIG ; BASE64 ESC \
```

The separators shown with spaces above are adjacent on the wire. ST (`ESC \\`)
is required; BEL, CAN, SUB, an interrupted sequence, or EOF discards the
request. Confirmed `3110;STATUSBAR;` messages are consumed even when malformed
or use an unknown operation. Other ELLO messages and near matches such as
`3110;STATUSBARX;` pass through unchanged.

`BASE64` is standard padded base64 encoding of:

```text
1;<session-token>;<complete-config-text>
```

The first two semicolons delimit the version and token. Everything after the
second is literal config content. `STATUSBAR` is the protocol namespace and
`CONFIG` is the operation, leaving room for other operations in the future.

Each session generates a random 16-byte token, exports it as 32 lowercase hex
characters in `STATUSBAR_SESSION_ID`, and replaces any inherited value for a
nested session. A request must contain the current token. The token prevents
incidental displayed output and requests copied from another session from
changing statusbar; it does not isolate statusbar from programs already running
inside that session. The sequence, token, payload, and config contents are
never forwarded to the outer terminal or written to the diagnostic log.

The complete OSC payload, from `3110` through the base64 text, is limited to
32,768 bytes. After the namespace, operation, envelope, and base64 expansion,
the largest config is 24,523 bytes. Oversized and invalid requests leave the
active config unchanged.

Replacement is transactional. Statusbar authenticates and parses the config,
prepares a new runtime, resizes the child PTY, and only then swaps it in. Line
count, commands, templates, styles, and colors can all change. Existing slot
overrides survive where their slot numbers still exist, and command results
establish a silent first baseline. Replacement uses the terminal's cursor save
slot, so an authenticated request received while the child owns the saved
cursor is held until the child restores it or its output pauses for 30 ms, the
same rule statusbar paints follow. Only the newest held request is kept, and child
output that follows it is processed against the old config until it applies.
There is no protocol reply.

Programs sending messages directly should serialize large writes so they do
not interleave on the terminal.

This document defines statusbar's behavior only. TJ currently owns its own OSC
3110 definitions and may consume unknown messages in that namespace. TJ
forwarding compatibility requires a future TJ change and is not claimed here.
